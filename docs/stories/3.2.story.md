# STORY 3.2: Validar ciclo de vida, compatibilidade e empacotamento

## User Story

**Como** usuário do QuantumScribe,
**quero** que o Liquid Orb e os temas existentes atravessem corretamente o
ciclo de vida do HUD em Windows e Linux,
**para** receber feedback visual confiável sem introduzir dependências gráficas,
de navegador, GPU ou rede no executável.

## Contexto

A Story 3.1 adicionou o renderer rasterizado `liquid_orb`, sua seleção e
persistência, a integração com `Popup` e o fallback para `atom_centered`. Esta
story fecha o trabalho do épico validando os caminhos que são mais sensíveis a
regressões: troca de tema, cancelamento, transições rápidas, sessão substituída,
compatibilidade entre plataformas e empacotamento.

O escopo é de validação e correções necessárias para atender aos contratos já
existentes. Não deve haver novo estado de negócio, API externa, banco, navegador,
GPU obrigatória ou alteração do tema padrão.

## Acceptance Criteria

1. Testes automatizados cobrem fallback, troca de tema, cancelamento, transições
   rápidas e sessão visual substituída, confirmando que callbacks de gerações
   antigas não alteram o HUD atual.
2. O `Popup` mantém as APIs usadas por `app.py` e os estados de gravação,
   transcrição, sucesso, erro e cancelamento continuam coerentes com `liquid_orb`
   e com os temas existentes.
3. A troca entre `liquid_orb`, `dots`, `atom`, `atom_compact`,
   `atom_centered` e `atom_minimal` não deixa itens visuais ou callbacks da sessão
   anterior ativos; `atom_centered` continua sendo o default.
4. A execução manual no Windows e no runner Linux valida o tema novo, os temas
   existentes, fallback, transparência, escala e transições rápidas, registrando
   as evidências e qualquer limitação ambiental.
5. O bundle Windows e o build Linux passam por smoke de empacotamento/importação
   offline e não exigem backend GPU, navegador, rede ou processo externo para
   iniciar o Core.
6. Os manifestos PyInstaller, os perfis de dependência e os locks usados pelo
   build permanecem coerentes; nenhuma dependência gráfica obrigatória nova é
   introduzida no Core.
7. `ruff check .`, `python -m compileall -q localwhisper main.py`,
   `python -m pytest -q`, `python -m pip check`, `pip-audit` e os inventários de
   empacotamento passam no checkout da alteração, com diferenças ambientais
   registradas.
8. A documentação da story, o File List, as evidências de validação e o status
   do épico são atualizados antes do handoff para QA.

## Dev Notes

### Previous Story Insights

- O renderer Liquid Orb já está isolado em `localwhisper/hud_effects.py`, usa
  Pillow em baixa resolução e retorna fallback seguro quando indisponível.
  [Source: `docs/stories/3.1.story.md#Completion Notes List`]
- A integração já protege callbacks por `_visual_generation`; esta story deve
  verificar o contrato em transições rápidas e sessões substituídas, não criar
  uma segunda máquina de estados.
  [Source: `docs/stories/3.1.story.md#Dev Notes`]

### File Locations

- `localwhisper/ui.py` concentra composição do `Popup`, estados visuais e
  scheduling por `root.after`.
  [Source: `docs/architecture/project-analysis.md#Relevant modules`]
- `localwhisper/settings_ui.py` mantém o catálogo e a seleção de temas; `config.py`
  persiste `hud_theme` e `atom_color`.
  [Source: `docs/architecture/project-analysis.md#Relevant modules`]
- Os testes de contrato e seam devem permanecer em `tests/`; validações de
  plataforma, build e updater permanecem nos módulos/scripts existentes.
  [Source: `docs/framework/source-tree.md#Regras de localização`]
- Os manifestos `QuantumScribe*.spec`, scripts de build e locks versionados são
  os pontos de validação do empacotamento.
  [Source: `docs/framework/source-tree.md#QuantumScribe`]

### Technical Constraints

- O runtime suporta Python `>=3.11,<3.14`, usa Tkinter/ttk, Pillow e PyInstaller;
  diferenças de SO ficam atrás dos adaptadores em
  `localwhisper/platform/{windows,linux}`.
  [Source: `docs/framework/tech-stack.md#Runtime`]
- O Core permanece offline, sem banco central ou API HTTP nova; dependências
  opcionais não podem entrar no caminho de inicialização.
  [Source: `docs/framework/tech-stack.md#Princípios de evolução`]
- Callbacks devem comunicar eventos ao thread de UI de forma segura e não podem
  atualizar widgets diretamente a partir de workers; `app.py` conserva suas
  fachadas durante a migração.
  [Source: `docs/framework/coding-standards.md#Limites de dependência`]
- Persistência, downloads e remoções devem continuar usando os controles
  atômicos e validações de caminho já definidos; logs não podem registrar áudio,
  texto ditado, tokens, credenciais ou dados pessoais.
  [Source: `docs/framework/coding-standards.md#Segurança e persistência`]
- O custo do renderer deve continuar compatível com rasterização em baixa
  resolução e atualização limitada; a rota WebGPU não faz parte desta story.
  [Source: `docs/architecture/recommended-approach.md#Rendering design`]

### Project Structure Notes

- A validação deve reforçar a fronteira existente: `Popup` controla ciclo de vida
  e estado, enquanto o renderer permanece uma seam de apresentação isolada.
  [Source: `docs/architecture/module-boundaries.md#Fronteiras atuais e alvo`]
- Não mover comportamento em massa entre módulos nesta story; qualquer refatoração
  estrutural deve permanecer isolada e acompanhada por contrato de caracterização.
  [Source: `docs/framework/coding-standards.md#Revisão`]
